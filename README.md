# Drive failure prediction — Backblaze & Toshiba

Two parallel predictive-maintenance pipelines over daily SMART telemetry: classify
"will this drive fail within N days?" and regress remaining useful life. Each notebook
trains a DNN and an XGBoost model on the same features so the two can be compared.

| notebook | data | input window |
|---|---|---|
| `Dataset_backblaze_Comparison.ipynb` | Backblaze quarterly releases (downloaded), Seagate only | 7-day deltas |
| `Dataset_Toshiba_Comparison.ipynb` | the local Toshiba export, 14 drive families pooled | 90-day window |
| `Dataset_backblaze_Window90.ipynb` | same Backblaze data, as raw daily **sequences** | 90-day window |
| `Dataset_Toshiba_Window90.ipynb` | the same Toshiba export, as raw daily **sequences** | 90-day window |
| `Dataset_backblaze_Analysis.ipynb` | the **whole Backblaze archive**, every model, with a **leakage audit** in front of it | 30-day window |

The window notebooks are a refactor of the first from row-level to window-level: a
sample is one drive's 90 consecutive days rather than one drive-day of hand-built
aggregates. Both are generated from `scripts/make_window_notebook.py` and both drive
`scripts/backblaze_window_pipeline.py` — same windowing, same models, same metrics.
They differ only in which frame they load and which SMART attributes exist in it
(the Toshiba families do not report `smart_187`, `188` or `241` at all).

`Dataset_backblaze_Analysis.ipynb` is the current end-to-end run and the one to read
first. It differs from every other notebook here in two ways that matter.

**It reads the whole archive, not a cohort.** Three yearly zips (2013-2015) plus one per
quarter from Q1 2016 on -- ~35 GB of zips, every manufacturer, every model, every drive.
`scripts/build_backblaze_archive.py` fetches them and reduces them to parquet shards
without ever extracting a CSV to disk. The earlier notebooks run on a *matched cohort*
(every failed drive plus a sample of healthy ones, so roughly half carry a failure);
this one runs at the fleet's real prevalence, a fraction of a percent of drive-days.
Precision figures from a cohort are inflated by construction; these are not.

**It evaluates every possible window.** A sample is one drive's 30 consecutive days,
labelled *does this drive fail within 30 days of the window's last day*. For validation
and test the start is enumerated at **stride 1** -- every offset in `[0, length - 30]`
for every drive in the split, nothing sampled and nothing skipped. That is hundreds of
millions of windows, which is why `scripts/archive_window_pipeline.py` exists: the
feature matrix is memory-mapped rather than held in RAM, the window index is computed
arithmetically rather than materialised, and the unit of work is a batch rather than a
window.

It also keeps the step the others assume: **before any feature reaches a model, every
column is scored against `failure` and the proxies are dropped.** The feature list is
derived from that audit rather than hard-coded, and training logs train loss / val loss
/ val PR-AUC / val ROC-AUC every epoch. It is generated by
`scripts/make_analysis_notebook.py`; `scripts/run_full_archive_analysis.py` is the same
three steps as a plain script.

### What the audit finds

No raw SMART attribute is a proxy — across the archive the strongest reach a rank AUC in
the 0.70–0.80 range, which is signal rather than an echo of the label. The leaks are
elsewhere:

| column | how it leaks | score |
|---|---|---|
| `days_to_last_record` and friends | `failure = 1` is written on a drive's **last reporting day**, so anything derived from a record boundary reconstructs the label | AUC 0.99 per drive-day |
| `still_reporting_at_export_end` | a drive still reporting on the archive's final day has not failed, so the probe restates the label | AUC 0.98 |
| `pod_slot_num` | leaks through *absence* — a rack slot stops being recorded once the disk is pulled | flagged on missingness |
| `vault_id`, `cluster_id`, `datacenter`, `capacity_bytes` | fleet topology, not drive behaviour; they describe where a disk sat and which generation it belonged to | blocked as suspect |

They are carried through ingest *precisely so the audit can score them*, then
blocklisted. `LeakageReport.assert_clean()` raises if any of them — or anything derived
from them — reaches `X`.

Coverage does the rest of the work. Backblaze has added and dropped SMART columns
repeatedly since 2013 — the 2013 files populate only five attributes — so an attribute
reported by a minority of the archive is dropped before leakage is even considered.

The audit is scored on a sample of **whole drives**, never a sample of drive-days:
every geometry probe is derived from a drive's own first and last day, and a drive whose
rows have been thinned has neither.

## The prediction app

```bash
python webapp/app.py        # http://127.0.0.1:5000
```

Drop in an `.xlsx`, `.csv` or `.parquet` of daily SMART telemetry — one drive or a whole
fleet — and every drive in it is scored on its own most recent window.

### What it serves

The default run is **`backblaze_2022x_w30`**: a 30-day window over the Backblaze fleet
from Q1 2022 on, predicting failure within 30 days of the window's last day. It carries
**two estimators trained on the identical windows**, and the app can run either or both:

| estimator | test PR-AUC | ROC-AUC | precision | recall | drive precision @100 |
|---|---|---|---|---|---|
| **XGBoost** (default) | **0.388** | **0.919** | 49.5% | 39.7% | **99 / 100** |
| CNN | 0.323 | 0.905 | 43.1% | 36.0% | 92 / 100 |

Measured on 3.09M held-out tiling windows at the fleet's real base rate of 0.24% — not on
a balanced cohort, where both numbers would be flattering.

Every run found in `models/` is offered in a dropdown, including the 90-day cohort models
and the full-archive run, so you can score the same file with each and compare. Two config
dialects are read transparently (`webapp/scoring.py`), so an older artifact set still
loads.

### What the page does

- **Model card** — both estimators side by side with their held-out metrics, the
  precision@K ladder, XGBoost's gain ranking, the leakage audit's per-channel AUCs, and
  the depth-123 decision tree that memorised its training set, as the argument for an
  ensemble.
- **Upload feedback** — a real progress bar while the bytes move (a 31 MB workbook is
  not instant), then a toast naming the file and what happened to it: drives scored,
  how many flagged, and any attribute that had to be imputed or drive that was skipped.
  Successes clear themselves and offer a jump to the ranking; failures stay put until
  dismissed. Nothing is ever silently accepted or silently dropped.
- **Results** — every drive ranked by `P(fails within 30 days)`, with the decision
  threshold drawn *on each risk bar* (XGBoost's is 0.217, so "low-looking" scores can
  still be `inspect`), an `inspect`/`hold` call, and a CSV export carrying both models'
  scores.
- **Head to head** — with both selected, the table shows both scores, and the header
  reports how many drives each flags alone and the rank correlation between them.
- **Retrospective check** — when the file carries a `failure` column, a precision@K panel
  scores the ranking against it. The column is never given to the model.
- **Input report** — rows read, drives found, date range, which of the 15 SMART
  attributes were present, and which drives were skipped and why.
- **Drive detail** — click any row for three things the table cannot show: the raw
  telemetry behind the score, the **risk trajectory** (the same model re-scored with the
  window slid back a day at a time, over 45 days, against the threshold — a drive
  climbing across it is deteriorating rather than merely unwell), and, for XGBoost, the
  **exact signed SHAP contribution** of each feature to that window's log-odds.
- **Provenance** — an expandable panel listing every blocked column and why, so it is
  visible on screen that the score never read them, even if your file contains them.

The app lays the uploaded rows on a dense daily calendar, replays the **saved** scaler —
not a freshly fitted one, which would be train/serve skew — and scores each drive's most
recent window. Nothing is written to disk and nothing leaves the machine.

### The investor site

`investor/` is a product site in front of this app: the problem, how the system works,

### Ready-made input

**Start with [`demo/`](demo/README.md).** Bigger, more realistic files than the built-in
chips — a 60-drive fleet with ground truth, a live snapshot with no answer key, truncated
windows — plus `demo/TEMPLATE.csv` and a guide to **getting your own telemetry in**:
the required schema, the fifteen SMART attributes and their `smartctl` names, and
`demo/from_smartctl/collect.py`, a tested daily collector that writes the app's format
directly. Rebuild with `python scripts/make_demo_data.py`.

The page itself offers one-click chips: six purpose-built files from `data/examples/`
(see that folder's README) and one real workbook per family from `data/Toshiba/`.

| example | demonstrates | result |
|---|---|---|
| `01_single_drive_healthy` | one clean 30-day window | risk 0.000, `hold` |
| `02_single_drive_failing` | a drive's final 30 days | risk 0.995, `inspect` |
| `03_small_fleet_mixed` | ranking, plus four blocked columns carried along | 4 of 6 failures in the top 4, all 6 in the top 9 |
| `04_partial_windows` | drives cut short mid-window | 2 scored by default, 8 with the checkbox |
| `05_missing_smart_columns` | only 5 of the 15 attributes | scores and warns; top risk 0.995 → 0.953 |
| `06_renamed_columns` | headers `time`/`serial`, no `failure` | aliases mapped; matches example 03 to six decimals |

`scripts/make_example_workbooks.py` rebuilds them. It reads the run the app serves rather
than a hard-coded attribute list, so the files track the model: regenerate them after
training a new one, or the app will median-fill inputs the workbooks never carried.

**Partial windows.** A drive that stopped reporting partway through holds fewer than 30
days. By default it is skipped, because a continuous window is what the model was trained
and calibrated on. That default hides exactly the drives a *historical* file is about —
the ones that failed are the short ones — so there is a checkbox to left-pad them and
score them anyway, down to a floor of 10 days, with every such row marked. On
`MG11ACA24TE/2025-09-22_2025-12-20.xlsx` that is the difference between 14 drives scored
and 17 — and all three of the drives it adds turn out to have failed, taking the file
from 4 recorded failures visible to 7. With it on, XGBoost puts five of those seven in
the top five.

Startup is under a second — every run in `models/` is loaded, but no data. A single-drive
workbook scores in well under a second; a 115k-row family workbook takes ~20s, nearly all
of it Excel parsing, for which `python-calamine` is about 6× faster than openpyxl here.
No network calls and no external assets, and uploads are parsed in memory and never
written to disk. Templates auto-reload, so editing `webapp/templates/index.html` needs
only a refresh.

Set `RUN=<prefix>` to change which run the app opens on, and `HOST` / `PORT` to move it.

`TOSHIBA_PIPELINE.md` is the detailed write-up of the Toshiba side — feature selection,
the 90-day window, and the class-imbalance bug that cost the most accuracy.

## Running things

```bash
# rebuild the Toshiba parquet from the xlsx export (~2 min)
python scripts/build_toshiba_parquet.py

# regenerate the Toshiba notebook after editing its generator
python scripts/make_toshiba_notebook.py

# regenerate the window notebooks (one generator, two datasets)
python scripts/make_window_notebook.py                    # Dataset_backblaze_Window90.ipynb
python scripts/make_window_notebook.py --source toshiba   # Dataset_Toshiba_Window90.ipynb

# fetch the whole Backblaze archive and reduce it to parquet shards.
# ~35 GB of zips over 45 archives; resumable, so an interrupted run picks up where it
# stopped. Nothing is ever extracted to disk -- CSVs are read from inside the zips.
python scripts/build_backblaze_archive.py --stage discover   # just list what exists
python scripts/build_backblaze_archive.py                    # download + shard

# the three-step analysis over the archive:
#   leakage audit -> every possible 30-day window -> training
python scripts/run_full_archive_analysis.py --quick   # smoke test on a coarse stride
python scripts/run_full_archive_analysis.py           # the real run (hours, GPU advised)

# ...or the same thing as a notebook, with the plots and the commentary
python scripts/make_analysis_notebook.py
python -m jupyter nbconvert --to notebook --execute --inplace Dataset_backblaze_Analysis.ipynb

# the older single-vendor cohort run (90-day windows over the Toshiba export)
python scripts/run_full_analysis.py --quick --epochs 3    # smoke test, ~3 min
python scripts/run_full_analysis.py                       # the real run, ~35 min on CPU

# the local prediction app: upload a workbook, get scores (needs models/)
python scripts/make_example_workbooks.py   # rebuild data/examples/ for the current run
python webapp/app.py                       # http://127.0.0.1:5000, then drop a file in
RUN=backblaze_window90 python webapp/app.py   # open on a different run
PORT=8080 python webapp/app.py                # move it

# run one end to end, writing the outputs back into the notebook
python -m jupyter nbconvert --to notebook --execute --inplace Dataset_Toshiba_Window90.ipynb

# 90-day sequence models — smoke test on generated data, no download
python scripts/backblaze_window_pipeline.py --synthetic --epochs 3

# ...and the real thing (downloads ~1.5 GB per quarter into data/)
python scripts/backblaze_window_pipeline.py --quarters Q1_2023 Q2_2023 --arch cnn --epochs 20
```

Requires `pandas`, `numpy`, `pyarrow`, `torch`, `scikit-learn`, `tqdm`, `matplotlib`,
plus `xgboost` and `python-calamine` for the notebooks, the parquet build and the app,
`openpyxl` to *write* the example workbooks, and `nbconvert` + `ipykernel` to execute a
notebook from the command line.

### Keeping the Backblaze downloads out of OneDrive

An extracted quarter is several GB and this project sits in a synced OneDrive folder.
Both the script and `Dataset_backblaze_Window90.ipynb` read `BACKBLAZE_DATA_DIR` and
stage the bulk data there; set it to somewhere unsynced before pulling real quarters:

```bash
export BACKBLAZE_DATA_DIR="$LOCALAPPDATA/Temp/backblaze_data"   # defaults to data/
```

The Toshiba data is small enough (690 MB, already committed to the folder) not to need
this.

## Note on the Toshiba numbers

The Toshiba export is a **cohort, not the fleet**: every failed drive plus a matched
sample of healthy ones. Ranking metrics (PR-AUC, Precision@K) transfer to production;
the absolute positive rate does not. See `TOSHIBA_PIPELINE.md`.
